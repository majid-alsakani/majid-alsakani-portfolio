Planner–Executor–Critic:
A practical architecture for reliable AI systems.

Complex tasks rarely fail because an LLM cannot write one answer. They fail because the system has no explicit plan, no execution boundary and no reliable way to tell a plausible answer from a useful one.

I use the Planner–Executor–Critic pattern when a task is too open-ended for a single model call but too important to leave to an opaque autonomous loop. The pattern gives an AI system three different responsibilities: decide what should happen, perform bounded work, and challenge the result before it reaches the user.

This is not a claim that every application needs agents. In fact, the best starting point is often a deterministic workflow or a single augmented model call. Anthropic makes the same distinction between predefined workflows and systems where the model dynamically directs its own process, and recommends adding complexity only when the task justifies the trade-off in latency, cost and control. [2]

The mental model

The simplest version looks like this:

Goal→Planner→Executor→Critic↺Approved result

The important detail is that the Critic does not merely ask the same model to “try harder.” It receives a contract, evidence and an explicit set of checks. When the result fails, the system sends structured feedback to the Planner or Executor instead of silently returning a polished error.

Architecture principleGive each step a narrower responsibility than the whole task. Reliability comes from the boundaries between steps, not from asking one prompt to do everything.

Why one LLM call is not enough

A single call is excellent for bounded transformations: classify this text, extract these fields, summarize this document. The shape changes when the request includes multiple goals, external tools, conflicting evidence or irreversible actions.

For example, “evaluate whether we should expand into a new market” may require research, data analysis, risk identification, assumption tracking and a decision draft. A single response can sound coherent while hiding missing evidence. Decomposing the work makes the system inspectable: we can see what it planned, what it actually executed, what evidence it used and why a reviewer accepted or rejected the result.

1. The Planner: convert intent into a contract

The Planner translates the user’s goal into a small, explicit plan. A good plan is not a long chain of vague prompts. It is a set of typed work items with dependencies, tools, expected outputs and stopping conditions.

Plan fieldPurpose
ObjectiveThe decision or artifact the system must produce.
TasksSmall units that can be executed and reviewed independently.
DependenciesWhat must exist before a task can start.
Evidence contractWhat counts as support and what remains an assumption.
Allowed toolsThe narrow set of tools the next step may call.
Exit criteriaConditions that stop expansion and prevent an endless loop.

The Planner should also be allowed to choose a simpler route. In Omni-Agent AI, the Auto mode distinguishes simpler tasks from work that benefits from multiple specialized agents. The goal is not to maximize the number of agents; it is to spend orchestration only where it improves the answer.

2. The Executor: do bounded work

The Executor turns a plan item into an action. It may call a search tool, inspect a CSV, query a database, transform a document or ask a specialist model to produce a structured artifact. The Executor should not be allowed to redefine the objective silently.

That boundary creates an important interface. The Executor receives an input such as:

{
  "task_id": "market-evidence-01",
  "objective": "identify evidence about demand",
  "allowed_tools": ["search", "csv_profile"],
  "output_schema": "EvidenceCard",
  "constraints": ["cite sources", "mark assumptions"]
}

It returns a result that can be stored, displayed and evaluated:

{
  "task_id": "market-evidence-01",
  "status": "completed",
  "evidence": [],
  "assumptions": [],
  "tool_trace": [],
  "confidence": "needs_review"
}

The exact schema will vary by product. The principle is stable: outputs should be data, not only prose. Structured results make retries, comparisons, auditing and UI rendering possible.

3. The Critic: challenge the result

The Critic is a quality boundary. It checks whether the output satisfies the plan, whether the evidence actually supports the claim, whether the tool use stayed within its permissions and whether the result is complete enough for the intended decision.

It is useful to separate at least three kinds of critique:

Contract review

Did the Executor return the required fields and follow the requested format?

Evidence review

Are claims grounded in retrieved or uploaded evidence, with assumptions marked?

Risk review

Could the result cause harm, leak data or trigger an action that needs a human?

A failed critique should be actionable. “Low quality” is not enough. The Critic should return a reason, the failed check, the relevant task and the smallest useful retry:

{
  "verdict": "revise",
  "failed_checks": ["missing_evidence_for_claim_3"],
  "feedback": "Add one primary source or downgrade the claim to an assumption.",
  "retry": {"task_id": "market-evidence-01", "scope": "claim_3"}
}

State and memory are part of the architecture

The loop needs a shared state that records the goal, plan, task outputs, tool traces, critique feedback and approval status. Without state, the system cannot explain what happened or resume after a failure.

Memory should be split by purpose. Session state is temporary working context. Episodic memory records what happened in a prior run. Semantic memory stores reusable facts or preferences. In Omni-Agent AI, the memory layer supports JSON session memory and vector-ready semantic retrieval. The Strategic Decision Twin adds an important governance boundary: a decision draft remains pending_human_review and is not promoted to semantic memory until explicit approval.

Failure modes to design for

Failure modeDesign response
Planner over-decomposesSet task budgets, depth limits and a simpler fallback path.
Executor drifts from the goalPass a typed task contract and reject outputs outside the schema.
Critic rubber-stampsGive it independent checks, evidence access and adversarial examples.
Memory contaminates a new taskSeparate session context from durable memory and label provenance.
Tool performs an external side effectUse allowlists, scoped credentials and explicit human confirmation.
Loop becomes expensiveMeasure latency and token cost per task; stop when the marginal value drops.

A small implementation sketch

The following pseudocode shows the control flow, not a framework-specific implementation:

state = load_state(request)

if should_use_simple_path(state):
    return single_step_answer(state)

state.plan = planner.create_plan(state.goal, state.context)

for task in state.plan.tasks:
    result = executor.run(
        task=task,
        tools=allowlisted_tools(task),
        state=state
    )
    state.results.append(result)

    critique = critic.review(
        task=task,
        result=result,
        evidence=state.evidence,
        contract=task.output_schema
    )

    if critique.verdict == "revise":
        state.feedback.append(critique)
        retry(task, critique, state)

final = synthesizer.compose(state.results, state.feedback)
return human_review_gate(final, state)

In a graph runtime, each major function becomes a node and the verdict becomes a conditional edge. LangGraph describes this kind of runtime as a low-level orchestration layer for long-running, stateful agents, with support for mixing deterministic steps and LLM-driven steps in one graph. [1]

How this maps to Omni-Agent AI

Omni-Agent AI implements the same architectural idea under a broader PRAR loop: Perception, Reasoning, Action and Reflection. In practical terms:

Planner–Executor–CriticOmni-Agent expression
PlannerOrchestrator and Strategic Planner determine the route and specialized work.
ExecutorResearcher, Analyst, Risk Manager and data agents execute scoped tasks with allowed tools.
CriticConsistency Review, synthesis and the Reflection stage challenge outputs before completion.
StateSession memory, task trace, agent status and tool log exposed in Command Center.
Human gateExternal actions and Strategic Decision Twin approvals require explicit human review.

This mapping is useful because it turns an abstract architecture into inspectable product behavior. A user can see which agents participated, which tools were allowed, what the system remembers and whether the result is still awaiting approval.

Production checklist

Before calling a Planner–Executor–Critic system production-ready, I would verify five things: every task has a bounded contract; every tool call is authorized and observable; critique failures lead to a targeted retry; memory has provenance and retention rules; and the system has an evaluation set that measures task success, not just fluent text.

I would also keep a simple path. If a single model call with retrieval solves the problem faster and more cheaply, use it. Complexity is not an achievement by itself. The architecture earns its place when planning, execution and critique create a measurable improvement in reliability, coverage or reviewability.
